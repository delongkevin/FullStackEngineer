# Color Match Challenge — Technical Q&A Documentation

## Overview

The Color Match Challenge is a browser-based cognitive game built with vanilla JavaScript, HTML5, and CSS3. Players are shown a color stimulus and must identify whether a displayed color name, hex value, or swatch matches the target within a countdown timer. The game tests color perception, cognitive processing speed, and accuracy under time pressure. It features timed rounds of increasing difficulty, progressive accuracy tracking, and a color theory engine that generates perceptually similar color distractors to make matching more challenging at higher levels.

- **Category:** Mobile / Web Game  
- **Tech Stack:** JavaScript (ES6+), HTML5, CSS3, Color Theory  
- **Live URL:** `/projects/color-match/index.html`  
- **GitHub:** https://github.com/delongkevin/FullStackEngineer

## 1. Architecture & Design Q&A

**Q1. How is the game's overall architecture structured?**

The Color Match Challenge uses a model-view-controller (MVC) inspired separation of concerns within a single-file or multi-file vanilla JavaScript architecture. The **model** is a plain JavaScript module (`colorEngine.js`) responsible for color generation, distractor selection, and difficulty parameterization. The **view** is the DOM rendering layer (`renderer.js`), which updates color swatches, labels, and timer displays. The **controller** (`game.js`) manages game state, processes player input events, evaluates answers, and drives the game loop. This separation ensures that the color theory logic can be tested in isolation and the UI can be restyled without touching game logic.

**Q2. How is game state represented and what are the valid game phases?**

Game state is a plain JavaScript object with the following fields: `phase` (one of `IDLE`, `COUNTDOWN`, `ROUND_ACTIVE`, `ROUND_END`, `GAME_OVER`), `currentRound`, `score`, `correctAnswers`, `totalAnswers`, `timeRemaining`, `targetColor`, and `choices`. The `phase` field acts as the game's finite state machine discriminant. Event handlers (timer tick, player click, start button) guard against processing input in invalid phases — for example, a player click is ignored if `phase !== 'ROUND_ACTIVE'`. Phase transitions are performed through a dedicated `setPhase(newPhase)` function that validates the transition and dispatches any side effects (starting the timer, playing a sound, showing an overlay).

**Q3. How does the color theory engine generate target colors and distractors?**

The color engine represents colors in the HSL (Hue, Saturation, Lightness) color space, which is more perceptually uniform than RGB for generating visually similar colors. A target color is selected from a curated pool of named colors defined by their HSL values and common names. Distractors are generated by perturbing the target's hue by a configurable `hueOffset` (e.g., ±15° on easy difficulty, ±5° on hard difficulty) and slightly varying saturation and lightness within a narrow band. This ensures that distractors are visually close to the target — challenging perception — while the correct answer remains objectively identifiable. At high difficulty, similar-named colors (e.g., "Crimson" vs. "Scarlet") are used as text distractors.

**Q4. What color spaces and models are used internally?**

Colors are stored internally as HSL objects `{ h: 0–360, s: 0–100, l: 0–100 }` for generation purposes and converted to CSS `hsl()` strings for rendering. For the "color name matching" round type, colors are also mapped to their nearest standard web color name using a pre-computed lookup table of ~140 named CSS colors with their approximate HSL centroids. Nearest-name lookup uses Euclidean distance in HSL space, which provides better perceptual results than RGB Euclidean distance for the hue dimension. Conversions between RGB and HSL use standard mathematical formulas implemented as pure utility functions.

**Q5. How is the countdown timer implemented precisely?**

The countdown timer uses `performance.now()` timestamps rather than decrementing a counter in `setInterval`. At round start, the `startTimestamp` is recorded. Each tick of the `requestAnimationFrame` loop computes `elapsed = performance.now() - startTimestamp` and derives `timeRemaining = roundDuration - elapsed`. This approach is drift-free: `setInterval` can drift by ±20ms per tick under load, leading to a timer that visually shows 1 second but actually takes 1.1 seconds. The rAF-based approach ties timer precision to the display refresh rate, ensuring the visual countdown and the actual deadline are always synchronized.

**Q6. How is progressive difficulty implemented across rounds?**

Difficulty increases as the player's round number increases. A `getDifficultyParams(round)` function maps round number to a parameter set: `roundDuration` (milliseconds), `hueOffset` (degrees of distractor separation), `numChoices` (number of answer options: 2, 3, or 4), and `challengeType` (swatch-only, name-only, or mixed). These parameters are evaluated fresh at each round start, so the transition is seamless. Players cannot skip difficulty levels, but exceptional accuracy in the current level causes difficulty to ramp more aggressively — the `hueOffset` is further reduced by `(accuracyPercent - 80) * 0.05` if accuracy exceeds 80%, providing adaptive difficulty.

**Q7. How is accessibility considered in the color-based game context?**

Since the game's core mechanic relies on color discrimination, it is inherently inaccessible to players with color vision deficiency (CVD) in its default configuration. To address this, the game includes a CVD-friendly mode that supplements color swatches with pattern overlays (stripes for red, dots for green, hatching for blue) enabling CVD players to distinguish colors by texture. This mode is toggleable via a settings panel. Additionally, all interactive elements have ARIA labels and are keyboard-navigable (Tab to move between choices, Enter to select), and the timer countdown is announced via ARIA live regions.

**Q8. How is accuracy tracked and computed over a session?**

Accuracy is computed as `(correctAnswers / totalAnswers) * 100`. Both `correctAnswers` and `totalAnswers` are incremented on every player response (a timeout with no response counts as an incorrect answer). The accuracy value is displayed as a rolling average updated after each round. At game end, the session summary shows round-by-round accuracy with a line chart rendered using SVG `<polyline>` elements, plotting accuracy on the Y-axis and round number on the X-axis. No external charting library is required.

## 2. Technology Stack Q&A

**Q1. Why are HSL color representations preferred over RGB for this game's logic?**

HSL (Hue, Saturation, Lightness) maps more closely to human color perception than RGB. In RGB space, shifting a color by equal amounts in each channel may produce a dramatically different perceived change depending on the base color. In HSL space, adjusting only the hue value produces a perceptually uniform rotation through the color wheel, making it straightforward to generate distractors that are "close but different" to the target. Saturation and lightness adjustments in HSL also have predictable perceptual interpretations (more/less vivid, lighter/darker), enabling fine-tuned distractor generation without trial-and-error.

**Q2. How are CSS custom properties used for dynamic color rendering?**

When a new target color is selected, the color engine sets CSS custom properties on the root element via `document.documentElement.style.setProperty('--target-color', hslString)`. Answer choice swatches are similarly updated by setting scoped custom properties on each choice element. This approach centralizes color updates to a single JavaScript call per round, and the CSS handles all rendering — no inline styles are set directly on DOM elements (other than the custom property assignment). This also enables smooth CSS transitions on the color swatches during round transitions using `transition: background-color 300ms ease`.

**Q3. What HTML5 APIs are specifically used?**

The project uses: `performance.now()` for high-resolution timing, `requestAnimationFrame` for the game loop, CSS Custom Properties for dynamic color application, SVG for the accuracy chart, `localStorage` for best score persistence, and the Web Audio API (optional) for audio feedback tones when a correct or incorrect answer is selected. The Web Audio API generates simple sine wave tones programmatically, requiring no audio file assets — the correct answer tone is a 440Hz A4 note, and the incorrect tone is a 300Hz lower note, both played for 150ms.

**Q4. How is the project structured as a set of files?**

```

├── index.html          # Entry point, HTML structure
├── css/
│   ├── game.css        # Game board layout and component styles
│   └── animations.css  # Keyframe animations for transitions

│   ├── renderer.js     # DOM update functions
│   ├── game.js         # Game controller, state machine, event handling
│   └── config.js       # Difficulty parameters, color database
└── assets/

```

**Q5. How is the code kept maintainable without a framework?**

Maintainability is ensured through: (1) ES6 modules with explicit `import`/`export` statements, allowing tree-shakeable separation of concerns; (2) JSDoc comments on all public functions describing parameters, return types, and usage examples; (3) a consistent naming convention (camelCase functions, SCREAMING_SNAKE for constants); and (4) pure functions for all color math — no functions in `colorEngine.js` have side effects, making them trivially testable and composable.

## 3. Features & Implementation Q&A

**Q1. How does the timed challenge mechanic work at a technical level?**

Each round begins when the `startRound()` function is called. It records `startTimestamp = performance.now()`, sets the `phase` to `ROUND_ACTIVE`, and begins the rAF loop. On each frame, `timeRemaining = roundDuration - (performance.now() - startTimestamp)` is computed. The timer bar width is set to `(timeRemaining / roundDuration) * 100` percent. When `timeRemaining <= 0`, the round ends automatically with the timeout counted as an incorrect answer. The round duration decreases from 5000ms at level 1 to 2000ms at level 10.

**Q2. How is the color name database structured?**

The color database is a JavaScript array of objects, each with: `name` (string), `h`, `s`, `l` (number), and `aliases` (array of alternative names). There are approximately 80 named entries covering the full hue spectrum at multiple saturation and lightness levels. The database is defined in `config.js` and imported by `colorEngine.js`. For each round, the target color is sampled from this array using a weighted random selection that avoids recently used colors, ensuring variety across a session.

**Q3. How is the player's response evaluated?**

Each answer choice is rendered with a `data-color-id` attribute corresponding to the index of that color in the choice array. When a player clicks a choice, the event handler reads `event.currentTarget.dataset.colorId`, looks up the corresponding color in the round's `choices` array, and compares it to the `targetColor.id`. If they match, the answer is correct. A visual highlight (green border for correct, red border for incorrect) is briefly applied to the selected and correct choices before transitioning to the next round.

**Q4. How does the accuracy tracking dashboard update in real time?**

After each round, the `renderer.updateStats()` function is called with the updated `correctAnswers` and `totalAnswers` values. The accuracy percentage is computed and the DOM text node is updated directly. The SVG accuracy chart adds a new data point: the round number is mapped to an X coordinate and the current accuracy percentage is mapped to a Y coordinate. A new `<circle>` element is appended to the SVG and the `<polyline>`'s `points` attribute is recomputed to include all round data points. This in-place SVG update avoids re-rendering the entire chart from scratch each round.

**Q5. How does the responsive design adapt to mobile screen sizes?**

The game board uses CSS Flexbox in a column direction for mobile viewports (< 600px width) and a row direction for tablets and desktops (> 600px). Color choice swatches are displayed in a 2-column grid on mobile and a single row on desktop, controlled by a CSS Grid with `auto-fill` columns. All sizes are specified in `clamp()` values — for example, `clamp(60px, 20vw, 120px)` for swatch size — ensuring smooth scaling between mobile and desktop without hard breakpoints. The timer bar spans the full width of the game container at all sizes.

## 4. Testing & Quality Q&A

**Q1. How are color theory functions tested?**

All functions in `colorEngine.js` are pure functions and are tested with Vitest unit tests. Key test cases include: `hslToRgb` and `rgbToHsl` round-trip accuracy (the converted value must be within ±1 unit of the original to account for floating-point rounding), `generateDistractors` ensuring distractors are never identical to the target, `nearestColorName` returning the correct name for known HSL inputs, and `getHueDistance` correctly computing the minimum angular distance on the 360° hue wheel (e.g., the distance between hue 10° and hue 350° is 20°, not 340°).

**Q2. How are game state machine transitions tested?**

The game state machine is tested by directly importing the `game.js` module in a jsdom environment, calling action functions (`startGame()`, `selectAnswer()`, `timeout()`), and asserting that the `phase` field transitions correctly. For example: calling `selectAnswer()` when `phase === 'IDLE'` should be a no-op; calling `startGame()` should transition from `IDLE` to `COUNTDOWN`; letting the timer expire should transition from `ROUND_ACTIVE` to `ROUND_END`. These tests use Vitest's fake timers to control `performance.now()` and `requestAnimationFrame` callbacks.

**Q3. How is color perception accuracy validated — i.e., are distractors "close enough" to be challenging but not indistinguishable?**

This is validated through a combination of automated hue distance assertions (distractors must be within the configured `hueOffset` of the target) and manual QA playtesting. Automated tests assert that `getHueDistance(target.h, distractor.h) <= hueOffset + 1`. Manual testing sessions at each difficulty level verify that distractors are perceptually distinguishable by players with normal color vision but require genuine attention at high difficulty. The `hueOffset` values were tuned empirically based on playtesting feedback.

**Q4. What performance benchmarks are targeted for the rAF-based timer?**

The timer update function must complete in under 2ms per frame to maintain 60fps. This is verified using Chrome DevTools' Performance panel — the `updateTimer()` call in the rAF callback is profiled and must not appear as a long task. Since `updateTimer()` only updates two DOM properties (a CSS custom property width and a `textContent` node), it consistently executes in under 0.5ms in modern browsers.

## 5. Security Q&A

**Q1. Are there any injection risks from the color database or dynamic content?**

No. The color database is a hardcoded JavaScript module, not external data fetched from an API or user-supplied JSON. Color names and HSL values are hardcoded strings and numbers that are inserted into the DOM via `textContent` (strings) and CSS custom properties (numeric values). No `innerHTML`, `eval`, or `document.write` is used. There is no attack vector for content injection.

**Q2. Does the game make any network requests?**

In its current implementation, the game makes no network requests at runtime. All data (color database, difficulty config) is bundled with the source code. There are no API calls, no analytics beacons, no CDN-hosted scripts. This makes the game fully operational offline and eliminates all network-layer attack surfaces (MITM, CSP bypass via CDN compromise).

**Q3. How should the game be hardened if it is extended to include a server-side leaderboard?**

If a leaderboard API is added, the following security measures are required: (1) Validate score data server-side against the game session parameters (round count, time limits) to reject implausible scores. (2) Rate-limit leaderboard submission endpoints to prevent spam and denial-of-service. (3) Authenticate users before accepting score submissions using a signed token (JWT). (4) Sanitize and validate all string inputs (username, display name) using an allowlist of permitted characters to prevent stored XSS in the leaderboard display.

**Q4. What CSP header is appropriate for this game in production?**

```
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'none'
```
`connect-src 'none'` is particularly strict and appropriate given that the game makes no network requests. This prevents any dynamically injected script from exfiltrating data. If the Web Audio API is used, no additional CSP directives are required, as it is a built-in browser API.

## 6. Source Code Update Guide

### Prerequisites
- A modern code editor (VS Code recommended with ESLint and Prettier extensions)
- Node.js 16+ for development tooling
- A local HTTP server (`npx http-server` or the VS Code Live Server extension)

### Steps

1. **Clone the repository:**
   ```bash
   git clone https://github.com/delongkevin/FullStackEngineer.git
   cd FullStackEngineer/projects/color-match
   ```

2. **Start the local development server:**
   ```bash
   npx http-server . -p 8080 -o
   ```

3. **Key files for common changes:**
   - Add or modify colors: `js/config.js` — edit the `COLOR_DATABASE` array
   - Adjust difficulty curve: `js/config.js` — edit `DIFFICULTY_LEVELS` array
   - Change distractor generation: `js/colorEngine.js` — modify `generateDistractors()`
   - Update visual styles: `css/game.css`
   - Update animation timing: `css/animations.css`

4. **Adding a new challenge type** (e.g., hex code matching):
   - Add `challengeType: 'hex'` to the relevant `DIFFICULTY_LEVELS` entries in `config.js`
   - Handle the new type in `renderer.js` `renderChoices()` function
   - Add a display format branch in `colorEngine.js` `formatColorDisplay()`

5. **Run tests:**
   ```bash
   npx vitest run
   ```

6. **Commit changes:**
   ```bash
   git add .
   git commit -m "feat: describe your change here"
   git push origin main
   ```

## 7. Build & Compile Instructions

The Color Match Challenge is pure HTML/CSS/JS and requires no compilation step. For production optimization:

1. **Install build dependencies:**
   ```bash
   npm install --save-dev terser clean-css-cli
   ```

2. **Create a `build.sh` script:**
   ```bash
   #!/bin/bash
   mkdir -p dist/js dist/css
   npx terser js/colorEngine.js js/renderer.js js/game.js js/config.js \
     --compress --mangle -o dist/js/bundle.min.js
   npx cleancss css/game.css css/animations.css -o dist/css/styles.min.css
   cp index.html dist/index.html
   # Update asset references in dist/index.html
   sed -i 's|js/colorEngine.js.*|js/bundle.min.js|g' dist/index.html
   sed -i 's|css/game.css.*|css/styles.min.css|g' dist/index.html
   echo "Build complete. Output in dist/"
   ```

3. **Run the build:**
   ```bash
   chmod +x build.sh && ./build.sh
   ```

## 9. Full-Scale Production Adaptation Notes

To evolve the Color Match Challenge into a production-quality, commercially viable product:

- **Adaptive Difficulty Engine:** Implement a machine learning model (e.g., a simple logistic regression or bandit algorithm) that personalizes the `hueOffset` and `roundDuration` parameters based on each user's historical accuracy, creating a truly adaptive challenge curve that maintains engagement in the "flow zone."
- **Color Vision Deficiency Support:** Expand the CVD-friendly mode with a full suite of Ishihara-inspired pattern overlays (deuteranopia, protanopia, tritanopia modes) and validate with actual CVD users through a user research program.
- **Leaderboard and Social Features:** Build a REST API (FastAPI or Node.js/Express) with PostgreSQL for persistent user accounts, score records, and a global leaderboard. Add social sharing (generating a shareable image of the session summary using the Canvas API).
- **Educational Mode:** Add an educational companion mode that explains color theory concepts — complementary colors, analogous colors, color harmony — as players progress, turning the game into a learning tool for designers and artists.
- **Native Mobile App:** Package with Capacitor for iOS and Android deployment, adding haptic feedback via the Haptics API and native platform UI conventions (bottom navigation bar on iOS, material design on Android).
- **Monetization:** For a commercial product, implement a freemium model — free access to levels 1–5 with an in-app purchase to unlock advanced levels and the adaptive engine, processed via Stripe or platform in-app purchase APIs.
- **Internalization:** Extract all hardcoded strings into locale files and integrate `i18next` for multi-language support, expanding the addressable market.
